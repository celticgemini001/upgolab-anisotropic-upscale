Upscaling One Axis: What Anisotropic Scale Actually Costs

Every upscaling guide talks about 2x, 4x, 8x — a single number. But a lot of real jobs are not square: a 4:3 clip that has to become 16:9, a phone photo whose width is fine and whose height is soft, an anamorphic source that was squeezed twice on the way in. This post measures what happens when you stretch one axis and leave the other alone.

15 November 2026 · synthetic 1080×720 reference + x264 encodes, measured with numpy and ffmpeg

The honest summary is in the first two lines and the rest of the article is the evidence. Axis count is a bigger lever than kernel choice: going from a two-axis 2x to a one-axis 2x gains 2.2 dB, while walking the whole kernel ladder from nearest to Lanczos gains 1.5 dB. And the "better" image costs more bytes at a fixed CRF, which is the part that bites when you ship a video instead of a JPEG.

Why this question is not academic

Most interpolation code takes two scale factors and most articles assume they are equal. They are equal in the resampler — you can pass (2.0, 2.0) or (2.0, 1.0) to anything — but they are emphatically not equal in information terms. Each axis carries its own frequency budget. If a source lost detail only horizontally, upscaling it vertically is doing work that was not needed, and every operation on an image costs something: interpolation smooths, and smoothing is irreversible.

So the practical question is:

  1. Is a one-axis stretch really cheaper in quality than a square one with the same area gain?
  2. Can you tell from the output which axis was damaged?
  3. Does it matter once a codec gets involved?
  4. Is the old "do 2x in two single-axis passes" advice worth anything?

Four questions, four experiments. Two of them came back negative, and I am reporting those as measured rather than dropping them, because a negative result is what stops you from optimising the wrong thing for a year.

The test scene: known answer, both axes exercised

PSNR is only meaningful against a reference that actually contains the detail you are trying to reconstruct. So the ground truth is generated at the target size, not upscaled from something smaller. It is 1080×720 and deliberately contains structure on both axes:

  • two low-frequency gradients, one varying in x, one in y, one diagonal;
  • a hard vertical edge (10 px wide) and a hard horizontal edge, so edge geometry can be measured separately per axis;
  • radial spokes in a ring — high frequency at every angle, not just the axis-aligned ones;
  • 14 thin vertical strokes (horizontal high frequency only) and 8 thin horizontal strokes (vertical high frequency only).

Degrading this three ways and reconstructing back to 1080×720 isolates the variable. All three reconstructions start from the same pixel budget and end at the same size; the only difference is which axis lost the information.

import numpy as np
from PIL import Image

def psnr(a, b):
    mse = np.mean((np.asarray(a, np.float64) - np.asarray(b, np.float64)) ** 2)
    return 99.0 if mse == 0 else 10 * np.log10(255.0 ** 2 / mse)

# GT is 1080x720. Build the three sources, then push each back to 1080x720.
srcs = {
    "both axes 2x":       GT.resize((540, 360), Image.LANCZOS),
    "horizontal only 2x": GT.resize((540, 720), Image.LANCZOS),
    "vertical only 2x":   GT.resize((1080, 360), Image.LANCZOS),
}
for label, s in srcs.items():
    for name, k in (("nearest", Image.NEAREST), ("bilinear", Image.BILINEAR),
                    ("bicubic", Image.BICUBIC), ("lanczos", Image.LANCZOS)):
        rec = s.resize((1080, 720), k)
        print(label, name, round(psnr(rec, GT), 2))

Read the gap between rows, then the gap along a row. Rows: neighbour (28.75) to Lanczos (30.27) is +1.52 dB. Columns: both-axes to single-axis, at any kernel, is +2.2 to +2.4 dB. The axis decision is worth more than picking the best resampler in the world — and unlike the kernel, you often cannot choose it, because it is set by the delivery format.

Notice also that horizontal-only and vertical-only land within 0.1 dB of each other (32.50 vs 32.60 at Lanczos). The scene has detail on both axes, so this is a fair test: the benefit comes from leaving one axis untouched, not from the scene happening to favour one direction.

Experiment 2 — can you tell which axis was damaged?

If you are handed a soft file and no metadata, the useful diagnostic is the ratio of horizontal to vertical gradient energy. Ground truth is 0.956 — slightly more vertical detail than horizontal, because of those 8 horizontal strokes.

Gradient means are 0–255 units; edge positions are sub-pixel centroids of the gradient profile.

The ratio moves in the direction you would predict and by about the same magnitude in both directions: 0.862 when vertical detail was destroyed, 1.071 when horizontal was. That is a 7–12% tilt away from the 0.956 baseline, which is small in absolute terms but one-directional and reproducible. A symmetric upscale leaves the ratio alone (0.960).

Two things surprised me here, and both are worth knowing before you trust a "sharpness" number:

  1. Both-axes reconstruction has more gradient energy than the ground truth — 2.106 and 2.193 against 1.641 and 1.717, roughly +28%. Lanczos overshoot does not recover detail; it manufactures contrast at the reconstruction edges. Any metric built on gradient magnitude will rank this smoothed-then-overshot image as "sharper" than the real thing. This is the same trap documented on the main upscaler guide, and it is why the table above reports the ratio rather than the absolute values.
  2. Edge position does not move. 406.60 px in ground truth, 406.44 px after reconstruction — one-sixth of a pixel, and identical for both one-axis cases. Single-axis interpolation on this scene does not shift geometry, so the fear that stretching one axis "pulls" the picture sideways is not supported. If you see a shift in production, it is coming from somewhere else in the chain, not from the resampler.

Experiment 3 — the better image costs more bytes

This is the measurement that changes how you ship. The same three reconstructions, encoded to H.264 with libx264 at CRF 20, one frame each at 1080×720:

reconstructionfile bytesPSNR after encode
both axes 2×18,59729.55
horizontal only 2×19,33431.07
vertical only 2×19,66831.25

x264, CRF 20, preset medium, yuv420p. PSNR measured after decode, against the ground truth.

+1.7 dB of quality costs +5.8% bytes (19,668 vs 18,597) at an identical CRF setting. That is not a bug or a rounding artefact — it is entropy. An image with more genuine detail has more to encode, and CRF holds quality per pixel rather than size per file, so a cleaner input produces a bigger file. The smoothed both-axes version is cheaper precisely because it is emptier.

The practical consequence. If you have a byte budget and you are choosing between a stretched axis and a squeezed one, the quality gain is real but you will pay for it in bitrate. Decide which constraint is binding before you upscale, not after you look at the file size and assume something went wrong.

Experiment 4 — "do it in two single-axis passes" changes nothing

There is long-standing advice that a 2× upscale should be performed as horizontal-then-vertical (or the reverse) because two 1D passes are cheaper and "cleaner" than one 2D kernel. Two 1D passes are indeed cheaper computationally — that part is trivially true — but the quality claim is what interests me.

small = img.resize((W // 2, H // 2), Image.LANCZOS)          # degrade
a = small.resize((W, H), Image.LANCZOS)                       # one pass
b = small.resize((W, H // 2), Image.LANCZOS).resize((W, H), Image.LANCZOS)  # horizontal 1st
c = small.resize((W // 2, H), Image.LANCZOS).resize((W, H), Image.LANCZOS)  # vertical 1st

The real photo is a 1080×1620 JPEG, degraded to half size and reconstructed. Same code path for all three.

On the synthetic scene the three results are identical to three decimal places. On the real photograph the largest difference is 0.006 dB — far below the level at which anyone could see it, and in the direction that favours the more expensive arrangement by an amount indistinguishable from rounding. The pixel-difference census agrees: 59.68% of pixels differ by more than 2 levels from the original in all three cases, max error 15, 15, 14.

So: use two passes if you are writing a fast resampler and want the speed. Do not use them expecting a quality improvement. On this evidence there is none, and the folklore that made you restructure your pipeline bought you nothing.

What to actually do

  1. Minimise the number of axes you touch. It is worth 2.2 dB — more than any kernel decision. If the delivery format allows it, crop or pad rather than stretch when only one axis is short.
  2. Never use nearest to save time on a gradient-heavy source. It is 1.5 dB behind Lanczos and the gap is consistent at every axis count measured here.
  3. Diagnose direction with the gradient ratio, not gradient magnitude. A sharpened or overshot image beats the ground truth on |dx| by 28% while being visibly softer. The ratio |dx|/|dy| is stable to about 1% and moves 7–12% when one axis is damaged.
  4. Budget bytes after the upscale, not before. A cleaner input raises the encoded size at fixed CRF. 5.8% in this test; assume the same order of magnitude on your own material.
  5. Do not split the pass for quality. Measured difference: ≤0.006 dB. Split it only for speed.

The wider point is the one that keeps showing up in these measurements: the number in the tool's UI ("4×") describes an output size, not a recovered amount. Which axis you scaled, and whether the source ever had detail there, decides the result — the multiplier on the label does not.

If you want to run this on your own file rather than my synthetic scene, the loop is the same three lines: degrade a known-good version of your footage along one axis, reconstruct it, and compare against the original instead of against the upscale you were about to ship. It takes about a minute and it will tell you whether the axis you were planning to stretch is the one that actually went soft — or whether, like the browser upscaler at upgolab.com, you should be re-running the whole frame rather than stretching a single direction of it.
